# Architectural Decisions

## ADR-001 — NestJS modular monolith
**Decision:** One deployable backend, business domains as modules under `src/modules/*`, not microservices.
**Reason:** Simpler ops/deploy for this project's scale; module boundaries give a migration path later if ever needed.
**Impact:** New domains (documents, comments, ...) are added as new modules, not new services.

## ADR-002 — PostgreSQL + TypeORM, `synchronize: false`
**Decision:** Migrations are the only way schema changes ship.
**Reason:** Predictable, reviewable schema history; `synchronize: true` is unsafe outside prototyping.
**Impact:** Every entity change needs a migration (`npm run migration:generate`, then hand-check FKs/partial indexes — TypeORM's generator misses both).

## ADR-003 — Access token in memory, refresh token in httpOnly cookie
**Decision:** Access JWT returned in the response body and held in a React ref only (never persisted). Refresh token is an httpOnly, `sameSite=lax` cookie, hashed at rest.
**Reason:** Avoids XSS-exposed tokens in localStorage; matches the "preferred browser architecture" requirement from the Stage 2 spec.
**Impact:** Full page reload loses the access token — `AuthProvider` silently re-fetches it via `/auth/refresh` on mount. See ADR-005 for why this can't happen in a Server Component.

## ADR-004 — Refresh token path is `/` (not `/api/auth`)
**Decision:** Broadened from an initial `/api/auth` scoping.
**Reason:** The frontend's `proxy.ts` runs on a different port/origin and needs to see the cookie on normal page navigations to gate `/workspace/*`; a path-scoped cookie was invisible to it.
**Impact:** Slightly larger cookie exposure surface (still httpOnly + sameSite). `COOKIE_DOMAIN` env var exists for cross-subdomain production deployments.

## ADR-005 — Server shell + client data island for authenticated pages
**Decision:** `/workspace` and `/workspace/[id]` are Client Components that fetch data after mount, rather than Server Components fetching with forwarded cookies.
**Reason:** Refresh-token rotation requires setting a cookie, which Next.js Server Components cannot do. Doing the rotation in a Server Component would desync the browser's cookie from the DB session on every render.
**Impact:** No true SSR for authenticated workspace data. Acceptable per Stage 2 scope; revisit only if SSR becomes a real requirement.

## ADR-006 — Workspace role resolved from DB, never trusted from JWT
**Decision:** JWT payload is `{sub, email}` only.
**Reason:** Roles can change after a token is issued; embedding them would mean stale permissions until the token expires (15 min window of incorrect access).
**Impact:** Every authorized request does a `WorkspaceMember` lookup (`WorkspaceMembershipGuard`). Verified live: promoting a user mid-session changes their effective permissions on the very next request, same token.

## ADR-007 — Immutable OWNER in Stage 2
**Decision:** OWNER cannot be removed, demoted, or leave; no ownership transfer endpoint exists.
**Reason:** Scoped out of Stage 2 to avoid an underspecified edge case (what happens to a workspace with zero owners).
**Impact:** Deliberate limitation — add ownership transfer as its own feature when needed, don't work around it ad hoc.

## ADR-008 — Invitation tokens hashed at rest; two accept/reject paths
**Decision:** Only `SHA-256(token)` is stored. Accept/reject support both `/invitations/:token/...` (email-link flow) and `/invitations/by-id/:id/...` (in-app flow, authorized by email match instead of the token).
**Reason:** A one-way hash means the raw token can never be shown again after creation — but the in-app "My Invitations" list (`GET /invitations/me`) still needs a way to act on invitations it can see.
**Impact:** Any future invitation UI should default to the `by-id` path unless it specifically has the raw token from a link.

## ADR-009 — 404-for-non-member, 403-for-insufficient-role
**Decision:** `WorkspaceMembershipGuard` throws 404 if the caller isn't a member; permission checks past that point throw 403.
**Reason:** Avoids confirming a workspace's existence to outsiders (existence disclosure), while still giving members clear feedback when they lack a specific permission.
**Impact:** Any new workspace-scoped endpoint should reuse `WorkspaceMembershipGuard` rather than inventing its own not-found handling.

## ADR-010 — Central `WorkspacePermissionsService`
**Decision:** All role-based rules live in one injectable service with explicit methods (not a generic capability-string dispatcher, not CASL/OPA).
**Reason:** Simple and explicit was preferred over a generic policy engine for this project's current complexity.
**Impact:** Stage 3 added `canCreateDocument`/`canEditDocument` (+ `assertCan*` throwing variants) here rather than a parallel system — VIEWER is read-only, every other role can mutate documents. No document-level ACL/override exists; add one only if a concrete requirement demands per-document permissions beyond workspace role.

## ADR-011 — Fractional position ordering; archive/restore acts on the whole subtree
**Decision:** Documents order via a `double precision` `position` column (midpoint bisection between siblings on insert/reorder, `POSITION_STEP = 1000` initial gap), not integer positions requiring renumbering. Archive and restore both operate on a document's **entire subtree** (BFS-collected via `collectSubtreeIds`, one bulk `UPDATE ... WHERE id IN (...)`), not just the target node.
**Reason:** Fractional positions mean reordering one document never touches unrelated rows — no "renumber the whole list" step. Whole-subtree archive keeps the LIST query a simple `archivedAt IS NULL` filter (Option A) instead of requiring a recursive/N+1 join to derive hidden-by-ancestor state at read time (Option B), which was the explicit N+1-avoidance requirement for Stage 3.
**Impact:** Restoring a document whose parent is still archived (or was itself deleted) reparents it to workspace root with a freshly computed position, rather than leaving it orphaned/invisible. Position rebalancing (in case of pathological repeated same-slot inserts) is not implemented — not a practical concern at Stage 3 scale, revisit only if evidence shows otherwise. There is no way to archive a single node while keeping its children active; if that's ever needed, it's a new decision, not a bug fix.

## ADR-012 — Sidebar reordering is buttons, not drag-and-drop
**Decision:** The Stage 3 document sidebar reorders siblings via explicit up/down buttons (calling the move endpoint with the adjacent sibling as `referenceId`), not drag-and-drop.
**Reason:** The backend move/reorder semantics (parentId + referenceId + placement) are drag-and-drop-ready, but implementing DnD state (drop targets, nesting-by-drop, visual feedback) risked destabilizing the tree UI within Stage 3's scope. Explicit controls exercise the same backend contract with far less UI risk.
**Impact:** Drag-and-drop can be added later as a pure frontend change — `moveDocument(apiFetch, workspaceId, documentId, parentId, referenceId, placement)` already supports arbitrary reparenting + positioning; no backend change would be needed. **Superseded by ADR-027 (post-Stage-10):** drag-and-drop was added exactly as predicted here, with zero backend changes. The up/down buttons stay too (now inside each row's overflow menu) as a keyboard/no-JS-drag-friendly fallback.

## ADR-013 — In-memory-only Yjs state; simplified full-state sync instead of step1/step2 negotiation
**Decision:** `CollaborationService` holds one `Y.Doc` + `y-protocols/awareness` `Awareness` per actively-open document in a plain in-memory `Map`, for the lifetime of the server process only - nothing is written to Postgres. On `join` (initial or reconnect), the server always sends the joining client `Y.encodeStateAsUpdate(ydoc)` as a single `sync-update` message, rather than implementing `y-protocols/sync`'s multi-step negotiation (client sends a state vector, server diffs and replies).
**Reason:** Stage 4's explicit scope is live sync + presence, not durability - Stage 5 owns snapshots/persistence. Applying `Y.encodeStateAsUpdate` on top of any existing client state is idempotent and commutative by Yjs's CRDT design, so a full-state bootstrap is *correct* for both a brand-new client and a reconnecting one; it just isn't bandwidth-optimal for very large documents, which the multi-step protocol would improve. Building the full negotiation now would be persistence-adjacent complexity ahead of the stage that actually needs it.
**Impact:** A server restart loses all in-memory collaborative state older than what's held in the still-connected clients' own `Y.Doc`s - there's no data-loss risk while at least one client stays connected across the restart, but a restart with zero connected clients does lose that document's live buffer. `CollaborationService.onModuleDestroy` at least tears down `Awareness`'s internal 30s interval timers cleanly on shutdown (a real leak found and fixed during Stage 4 testing) - it does not persist anything. **Superseded by ADR-014 (Stage 5):** the durable store this note called for now exists; the simplified full-state sync-on-join choice stands unchanged.

## ADR-014 — Durability buffer as one upserted row; restore via content replacement, not CRDT merge
**Decision:** `document_versions` stores full `Y.encodeStateAsUpdate` blobs (binary, never JSON), discriminated by `kind`. The `AUTO` kind is upserted in place - exactly one row per document at all times, enforced by a partial unique index `(documentId) WHERE kind = 'auto'` - rather than an append-only update log with periodic compaction. Writes are trailing-throttled (`CollaborationPersistenceService.scheduleFlush`, default 3s), not one write per keystroke. Restoring a version does **not** `Y.applyUpdate` the old bytes into the live doc (a CRDT merge can only add operations, never remove ones made since) - instead `replaceBlocksContent` deletes and reconstructs the live doc's block list from a decoded copy of the target version, inside one transaction, and the resulting diff is broadcast to the room.
**Reason:** An upserted single row avoids both "full snapshot on every keystroke" and the replay-time growth of an ever-growing update log - Postgres storing one occasionally-updated blob per document is simple and cheap at this project's scale. Content-replacement is the only correct way to make an old CRDT state become the new current state while staying inside Yjs's own document (so the diff naturally propagates to connected clients via the existing sync-update transport) - merging would layer the old content on top of the new instead of replacing it.
**Impact:** `yjs-document.util.ts` (`decodeState`/`encodeBlocksSnapshot`/`replaceBlocksContent`) has narrow, documented knowledge of the block schema (id/type/text/checked/level/language/imageUrl/imageAlt) purely to clone content across `Y.Doc` instances - if `frontend/src/features/collaboration/blocks.ts`'s schema changes, this file must change with it. A true production system at much higher write volume might prefer an append-only update log + periodic compaction instead (listed as a known limitation) - not needed at this scale. Every restore first captures current state as a `RESTORE_POINT` version, so restoring never destroys history, satisfying the explicit no-data-loss requirement.

## ADR-015 — Notification idempotency via a unique `dedupeKey`, not BullMQ alone
**Decision:** Every notification-triggering event (mention, reply, resolve, reopen) computes a deterministic `dedupeKey` string and passes it both as the BullMQ `jobId` (`queue.add(name, payload, {jobId: dedupeKey})`) and as a unique DB column inserted via `INSERT ... ON CONFLICT (dedupeKey) DO NOTHING` (`NotificationsService.createIfNotExists`). `dedupeKey` segments are joined with **underscores**, and timestamps use `Date.getTime()` (epoch ms), never `.toISOString()`.
**Reason:** BullMQ's `jobId`-based dedup only holds while the original job is still known to the queue (bounded by `removeOnComplete`/retention) - it is a cheap first line of defense, not a durable guarantee. The DB unique constraint is what actually survives retries, redeliveries, and job-retention expiry. The underscore-only rule exists because BullMQ hard-rejects (`"Custom Id cannot contain :"`) any custom `jobId` containing a colon - a real runtime bug hit during Stage 6 development, since `.toISOString()` timestamps contain colons (`15:34:22`) and an early version of the resolve/reopen `dedupeKey` used colons as delimiters.
**Impact:** Any future notification-triggering event must build its `dedupeKey` the same way (underscore-delimited, no colons, no `.toISOString()`) or it will crash BullMQ's `.add()` call at the exact moment the triggering action (e.g. a comment) has already committed to Postgres - `CommentsService.safeEnqueue` exists specifically to stop such an enqueue failure from being surfaced as a failure of the (already-successful) comment request, logging instead of throwing.

## ADR-016 — Dual MinIO endpoints: internal for the backend, public for presigned URLs
**Decision:** `MinioService` holds two `minio` SDK `Client` instances: `client` (internal Docker hostname, e.g. `minio:9000`, used for `statObject`/`removeObject`/bucket setup) and `publicClient` (browser-reachable host, e.g. `localhost:9000`, used **only** for `getPresignedUploadUrl`/`getPresignedDownloadUrl`). Both are configured with `region: 'us-east-1'` explicitly. `MinioConfig` gained `publicEndpoint`/`publicPort`/`publicUseSSL`, each defaulting to the corresponding internal value when unset.
**Reason:** A presigned URL is handed directly to a browser client, which cannot resolve the internal Docker network hostname the backend itself uses to reach MinIO - discovered live when Stage 6 became the first feature to actually exercise `getPresignedUploadUrl`/`getPresignedDownloadUrl` (they existed since Stage 1/2 but were unused until now) against the real `docker compose` stack: uploads failed with the presigned URL pointing at `http://minio:9000/...`. The explicit `region` is required too - without it, the minio SDK's presign path makes a live `getBucketRegion` network call *to the client's own configured endpoint* to auto-detect the region, which then fails for the same reachability reason when the public endpoint isn't reachable from inside the container; setting the region short-circuits that lookup entirely.
**Impact:** `docker-compose.yml`'s `backend` service sets `MINIO_PUBLIC_ENDPOINT=localhost` / `MINIO_PUBLIC_PORT=${MINIO_HOST_PORT:-9000}`; non-Docker local dev (where MinIO is already reachable at the same host as the backend) needs no new env vars, since the public values default to the internal ones. Any future code needing a MinIO client for browser-facing URLs must go through `publicClient`/the two presign methods, never `client` directly.

## ADR-017 — Publishing model: latest state, not a snapshot; on-demand + time-based revalidation
**Decision:** Publishing a document (`Document.isPublished`/`publicSlug`/`publishedAt`, no new table) never copies content anywhere - the public read path (`PublicDocumentsService.getPublished`) always decodes whatever is currently in the durable Yjs buffer (`CollaborationPersistenceService.hydrate`) at request time. Publish/unpublish/republish/archive call a new `RevalidationService`, which `POST`s a shared-secret-protected request to the frontend's `/api/revalidate` Route Handler, which calls `revalidateTag(tag, {expire: 0})` + `revalidatePath` for the affected slug(s). The public page's `fetch` also carries `next: {revalidate: 60, ...}` as a time-based fallback. Ordinary content edits (typing in the collaborative editor) do **not** individually trigger a revalidation call.
**Reason:** Model B (publish = snapshot a specific version, require republish to expose edits) would need a second durable copy of content, duplicating what `document_versions`/`CollaborationPersistenceService` already does, and would surprise editors who expect "publish" to mean "what's live right now, kept live" - the simpler, more intuitive model for a Notion-style collaborative doc. Reusing the existing durability buffer as the single source of truth for public reads (rather than introducing a "published snapshot" table) follows the project's established reuse-don't-duplicate posture. On-demand revalidation for the publish-state-transition actions gives instant correctness for the events that matter most (a document going public/private, or its slug changing); coupling revalidation into every throttled Yjs persistence flush would be much deeper, riskier integration for comparatively little benefit, so the 60s time-based window is the accepted freshness bound for ordinary content edits instead.
**Impact:** A visitor can see content update on a public page within 60s of an edit without the editor doing anything; publishing/unpublishing/changing the slug is reflected on the next request, not after a delay. If a future stage needs instant reflection of every keystroke on the public page too, that's a new, deliberate decision (e.g. broadcasting from `CollaborationPersistenceService.flush` to a revalidation call), not a bug to silently patch here. `RevalidationService.revalidateSlug` never throws - a failed call is logged/metriced only (`public_revalidation_failures_total`), same rationale as `CommentsService.safeEnqueue` in ADR-015: it's a secondary side-effect of an already-committed state change. This required a second internal/public URL split, alongside ADR-016's MinIO one: `AppConfig.frontendInternalUrl` (Docker DNS, `http://frontend:3000`) for this backend→frontend call, distinct from `frontendUrl` (browser-facing, used for CORS/invitation links) - found live the same way as ADR-016, by actually exercising the call against the real Docker stack and watching it fail to resolve the browser-facing hostname from inside the backend container.

## ADR-018 — `proxy.ts` gates `/p/*` to guarantee a real 404 status code
**Decision:** `proxy.ts` (previously scoped only to `/workspace/:path*`) now also matches `/p/:path*`. For those requests, it calls the backend's public-documents API directly (`cache: 'no-store'`) and returns a bare `404 Not Found` response itself, before any page rendering starts, if the backend says the slug doesn't resolve.
**Reason:** Found live, not anticipated: the app has a root `app/loading.tsx`, which Next.js uses to wrap *every* route (including `/p/[slug]`) in an implicit `<Suspense>` boundary. Streaming SSR commits the response's HTTP status (200) as soon as that Suspense boundary's fallback would be shown, which happens before `/p/[slug]`'s own `await fetch(...)` and `notFound()` call resolve. Next.js 16's own bundled docs confirm this is expected, documented behavior ("Calling notFound() after streaming has started" / "Status Codes" in the `loading.js` reference) with the exact recommended fix: run the existence check in `proxy`, since that runs before the response is committed. Without this, the page's *content* was already correct (real not-found UI, `noindex` meta tag - Google's own guidance says this doesn't hurt indexing), but the literal HTTP status curl/monitoring/tests would observe was `200`, not `404`.
**Impact:** Every `/p/:slug` request now costs one extra backend round-trip (the existence check in proxy, `cache: 'no-store'` by design - it must reflect true current state) on top of the page's own data fetch; acceptable at this project's scale, and explicitly the trade-off Next's own docs recommend over losing correct status codes. If the backend is unreachable, proxy fails open (passes the request through) rather than taking down the entire public site on a transient error - the page's own fetch will then hit the same 200-status caveat, a known, accepted degradation, not a silent failure. Any future dynamic public route with the same shape (fetch-then-maybe-`notFound()`, wrapped by the root loading boundary) needs the same proxy-level check if a correct status code matters for it.

## ADR-019 — Postgres full-text search via a generated `tsvector` column; indexing only from durable state
**Decision:** No new search infrastructure (no Elasticsearch/Meilisearch/Typesense). `documents` gained a GENERATED ALWAYS `searchVector tsvector` column (`setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', contentText), 'B')`, STORED, GIN-indexed) plus a plain `contentText text` column (`select: false`, mirrors `User.passwordHash`). Postgres auto-maintains `searchVector` on every `title`/`contentText` write - no app-level "keep the index in sync" code for `title`. `contentText` is written from exactly one place: `CollaborationPersistenceService.flush()`, immediately **after** a successful durability-buffer write, by decoding the just-persisted bytes (`decodeState`/`encodeBlocksSnapshot`) and joining block text - never from the live in-memory `Y.Doc`. `DocumentsService.search()` uses `websearch_to_tsquery` (parameterized, natural query syntax) + `ts_rank` for ordering + `ts_headline` for snippets, scoped by `workspaceId` and `archivedAt IS NULL`.
**Reason:** The task's own explicit guidance was to prefer Postgres FTS over a new infrastructure dependency unless the original requirements demanded an external engine - they didn't. Indexing from the durable buffer (not the live session) was an explicit hard requirement (search must not depend on an active collaboration session) and reuses Stage 5's existing "durable buffer is the canonical current-content source" pattern (the same one `PublicDocumentsService` already relies on) rather than inventing a second content-extraction path. Running the index update at the same trailing-throttled cadence as the durability flush means search freshness has the same, already-understood latency characteristics as the durability guarantee itself - no new timer/polling infrastructure.
**Impact:** A very recent edit's content is searchable only after the next durability flush fires (same window as durable-persistence lag, typically a few seconds - `COLLAB_PERSIST_INTERVAL_MS` in tests), not instantly on keystroke; this was the explicit intent, not a bug. `contentText` is capped at 20,000 characters (`MAX_CONTENT_TEXT_LENGTH`) before being written - a pragmatic bound, not a hard product requirement. A real TypeORM pitfall was found while building the query: `.getRawAndEntities()` combined with a manually-aliased `.addSelect('d.id', 'docId')` silently produced wrong results (missing `id`, always-null `snippet`) due to TypeORM's internal entity-column auto-aliasing colliding unpredictably with the manual alias - fixed by abandoning mixed entity+raw hydration entirely in favor of a fully-explicit `.select()`/`.addSelect()` per field + `.getRawMany<{...}>()`. Any future querybuilder work needing both computed SQL expressions (`ts_rank`, `ts_headline`) and entity fields in the same row should default to this fully-explicit-raw approach rather than `getRawAndEntities()`.

## ADR-020 — Entitlements as a service orthogonal to authorization; transactional locking for hard limits; downgrade never deletes data
**Decision:** `EntitlementsService` (plan/limit checks: `assertCanCreateDocument`/`assertCanInviteMember`/`assertCanUploadAttachment`/`assertFeatureEnabled`) is a separate service from `WorkspacePermissionsService` (role checks) - both must independently pass; nothing merges them into one "can this user do X" call. `PLAN_LIMITS` (FREE: 5 members/50 documents/100MB/no manual snapshots; PRO: unlimited/unlimited/10GB/manual snapshots) lives in one config object, never duplicated as inline numbers anywhere else. Document-creation and member-invitation limits get full transactional rigor: the caller locks the `Workspace` row (`SELECT ... FOR UPDATE` via `EntitlementsService.lockWorkspace`) inside its own transaction *before* calling the count-based assertion, serializing concurrent requests at the exact limit boundary. Attachment storage uses a lighter count-then-check with no lock (accepted, documented race window - uploads are already a two-phase async/best-effort flow). Billing is a `Subscription` row keyed 1:1 to `workspaceId` (not per-document), created transactionally alongside every new workspace. The mock payment provider (`PaymentProvider` interface + `PAYMENT_PROVIDER` injection token) and the idempotent webhook core (`BillingService.applyEvent`, unique `BillingWebhookEvent.eventId` + `INSERT ... ON CONFLICT DO NOTHING`) are designed so a real Stripe integration would only replace `MockPaymentProvider` and delete the dev-only `mock-pay` shortcut - `applyEvent`/the webhook controller stay as-is. Downgrading to FREE (`BillingService.downgradeToFree`) only flips `plan`/`status`/`currentPeriodEnd` columns - there is no document/member/attachment deletion code anywhere in the downgrade path.
**Reason:** Keeping entitlement and authorization as two independently-enforced checks (mirroring the task's own framing: "is this user allowed" vs. "does this plan permit it") avoids a single service accumulating two unrelated axes of logic, and lets either evolve without touching the other - a future third plan tier changes zero authorization code. Transactional row-locking on the two true hard invariants (document/member counts) is what actually prevents a straightforward TOCTOU race (two requests both read count=49, both see "below the limit of 50", both insert) from letting a workspace exceed its limit under concurrent load - a plain count-then-check without the lock is provably unsafe under Postgres's default read-committed isolation, which was verified live with 5 concurrent document-creation requests fired at the last available slot (exactly one 201, four 403s). Deleting nothing on downgrade is possible *by construction*, not because of extra cleanup code: every future create/invite/upload attempt re-evaluates the same count-based check fresh, so an over-limit workspace simply can't add new resources until it's back under the limit or re-upgraded - existing resources stay fully readable/usable with zero special-cased "downgrade" logic.
**Impact:** Two real bugs were found and fixed while building/testing this: (1) `GlobalExceptionFilter` was silently stripping every field beyond `message`/`error`/`statusCode` off a thrown `HttpException`'s body, which meant `EntitlementsService`'s structured `PlanLimitExceededPayload` (`code`, `limitType`, `limit`, `current`, `plan` - exactly what a frontend "upgrade to PRO" CTA needs) never reached the client; fixed by having the filter preserve any extra fields on the exception body alongside the standard shape. Any future service that attaches structured data to a thrown exception can now rely on it surviving the global filter - this wasn't true before Stage 8. (2) `BillingService.applyEvent`'s idempotency check read `result.identifiers.length > 0` to mean "row was inserted", but TypeORM's `orIgnore()` (`ON CONFLICT DO NOTHING`) returns one `identifiers` entry **per input row regardless of outcome** - `[null]`, not `[]`, on a skipped duplicate - so the old check treated every duplicate webhook delivery as newly-applied, silently re-running `applyEvent`'s side effects on redelivery. Fixed to `result.identifiers.some((id) => id != null)`; the unit test fixture was also corrected to return `[null]` (not `[]`) for the duplicate case, since the wrong fixture shape is exactly what let the bug ship unnoticed by unit tests - caught only by an e2e test that delivered the same webhook `eventId` twice. Any future `orIgnore()`/`ON CONFLICT DO NOTHING` insert must check for `null` entries, not array length, to detect a skipped row.

## ADR-021 — Shared modal/panel infrastructure instead of three duplicated implementations; notification workspaceId via join, not a stored column
**Decision:** Stage 9 introduced `components/ui/SlideOverPanel.tsx` (Comments/Versions/Attachments panels all now render through this one component instead of each owning its own overlay/header/close-button markup) and `components/ui/ConfirmDialog.tsx` (used for document-archive confirmation), both built on a new shared `lib/useFocusTrap.ts` hook (Tab-wraps focus inside the container, Escape closes) - also retrofitted onto `SearchDialog`. A new `components/ui/ToastProvider.tsx`/`useToast()` (mounted once in the root layout) is the app's only toast mechanism. Separately, `NotificationsService.list()` now joins `documents` to return a `workspaceId` alongside each notification (added to `NotificationResponseDto`), rather than adding a `workspaceId` column to `Notification` itself.
**Reason:** Three panels had independently reinvented the same overlay/header/close-button shape with zero focus management (Tab could escape to the page behind an "open" panel, no `role="dialog"`) - fixing that three times, slightly differently each time, is exactly the kind of drift a shared component prevents; fixing it once in `SlideOverPanel`/`ConfirmDialog`/`useFocusTrap` fixes it everywhere at once and for any future panel. Archiving was one click with no confirmation despite taking an entire subtree with it - `ConfirmDialog` closes that gap without inventing a heavier design-system dialog than this project needs. For notifications, `workspaceId` is a stable, derivable fact of `documentId` (a document never changes workspace) - storing it redundantly on every `Notification` row would be a second source of truth for data the `documents` table already owns; a join at read time has no correctness downside and needed no migration.
**Impact:** Any future modal/panel-shaped UI should default to `SlideOverPanel`/`ConfirmDialog` rather than hand-rolling another overlay - this is now the established pattern the way `features/*/api.ts` is for API calls. `useFocusTrap` is a generic hook (`RefObject`, `onEscape` callback) so it isn't tied to any one component's markup. The `NotificationsService.list()` query is the same explicit `.select()`/`.addSelect()` + `.getRawMany()` shape ADR-019 already established for `DocumentsService.search()` (never `getRawAndEntities()` when a computed join column is involved) - and while building it, the exact same `orIgnore()` "`.length` vs. non-null" bug from ADR-020 was found a second time in `NotificationsService.createIfNotExists` (the DB constraint still prevented the actual duplicate row; only the "created" vs. "duplicate" metric/log was wrong). Both are fixed. Any future `INSERT ... ON CONFLICT DO NOTHING` in this codebase should be written expecting `[null]`, never `[]`, for a skipped row from the start.

## ADR-022 — Document-level ACL as a second orthogonal axis, not a rewrite of workspace roles
**Decision:** `DocumentPermissionsService` + a new `document_collaborators` table (`documentId`, `userId`, `accessLevel: VIEWER|EDITOR`, unique per pair) + a new `documents.restricted` boolean layer a per-document override on top of the existing workspace-role bar. OWNER/ADMIN always pass regardless. With no override, `restricted=false` (the default) behaves exactly as every pre-existing document already did. Managing the ACL (toggling `restricted`, sharing/unsharing) is its own new permission (`WorkspacePermissionsService.canManageDocumentAccess`, OWNER/ADMIN), not folded into `canEditDocument`.
**Reason:** The requirement ("a user's access to a document may differ from their workspace role") is a second axis, not a replacement for the first - exactly the same shape as `EntitlementsService` vs. authorization (ADR-020) and worth the same separation for the same reason: either can evolve independently, and nothing about workspace-role logic had to change to add this. Defaulting `restricted` to `false` was a deliberate zero-migration-risk choice - every document that existed before this feature keeps behaving identically; the ACL is opt-in per document, not a retrofit that could silently change existing access.
**Impact:** `DocumentsController` re-fetches the document (already-fetched DTO, not a second entity query - `DocumentResponseDto` gained `restricted` for exactly this) and calls `documentPermissions.assertCanView`/`assertCanEdit` alongside the existing `assertCanEditDocument` role check on every mutation/read endpoint; `list()`/`search()` results are filtered through `filterVisible` so a restricted document's title/snippet never reaches a non-shared caller. The identical `resolveAccess` call is reused in `CollaborationGateway.handleJoin` (see ADR-013's authorization pipeline) - one implementation, enforced at both the REST and realtime boundary, not two parallel checks that could drift.

## ADR-023 — Public edit-by-link: mode + expiry as plain document fields, not a new sharing entity
**Decision:** `documents.publicAccessMode` (`'view'`|`'edit'`, default `'view'`) and `documents.publicExpiresAt` (nullable timestamptz) extend the existing Stage 7 publish fields (`isPublished`/`publicSlug`/`publishedAt`) rather than introducing a separate "share link" table. `PublishDocumentDto` gained optional `mode`/`expiresAt`; `findPublishedBySlug` (used by both the public REST read and `join-public`) treats an expired link exactly like an unpublished one - `null`, never a distinguishing 404-vs-410 signal that would leak whether a slug ever existed. Anonymous editing goes through a new `join-public {slug}` gateway event (see `01-architecture.md`), not a new REST endpoint - editing is inherently a realtime CRDT concern, so it reuses the same `/collab` transport and room-per-document isolation every authenticated edit already goes through.
**Reason:** Publishing is already 1:1 with a document (ADR from Stage 7 - no new table for the original view-only case); `mode`/`expiresAt` are just two more attributes of that same 1:1 relationship, not a new kind of object requiring its own lifecycle/table. `handleConnection` was changed to tolerate a *missing* token (anonymous) while still rejecting an *invalid* one - the minimal change that lets an anonymous socket survive long enough to attempt `join-public`, without weakening the authenticated `join` path's own `!user` check.
**Impact:** An edit-by-link session's authorization is entirely "does a published, non-expired, edit-mode document exist at this slug" - there is no workspace membership, no role, no path from that session to any other document. Frontend: `usePublicCollaboration` is a deliberately separate hook from `useCollaboration` (not a shared-with-an-`if`-branch implementation) - the two auth models don't share enough (no role, no per-user presence, no reconnect-with-token) to make one implementation clearer than two small ones. `PublicDocumentResponseDto` gained a `mode` field so the frontend knows which renderer to use - the one intentional, minimal public-response-shape expansion since Stage 7 (existing e2e test asserting the exact key set was updated, not weakened, to include it).

## ADR-024 — Search indexing moved off the edit-flush path onto a BullMQ queue, re-reading durable state rather than trusting the enqueue-time payload
**Decision:** `CollaborationPersistenceService.flush()` no longer decodes Yjs state and writes `documents.contentText` inline; it enqueues a `{documentId}` job onto the (previously reserved but processor-less) `QueueName.SEARCH_INDEX` queue, with `jobId: documentId` so a burst of edits to one document coalesces into at most one pending job. `SearchIndexProcessor` (new, lives in the collaboration module to avoid a documents↔collaboration circular import) does the actual decode + `DocumentsService.updateSearchContent` call, and deliberately re-hydrates the *current* durable buffer itself rather than being handed the state that was current at enqueue time.
**Reason:** The task requires the index update to happen asynchronously via a queue, not inline in the request/flush path. Re-reading the durable buffer inside the processor (rather than serializing the Yjs bytes into the job payload) is what makes the processor trivially idempotent and duplicate-safe: two jobs for the same document, processed in any order, both converge on whatever the durable buffer holds *at the time each one runs* - there is nothing to "duplicate" the way an INSERT could conflict, so no dedupe key or unique constraint was needed the way `Notification.dedupeKey` (ADR-015) needed one for a true insert.
**Impact:** A job that finds no durable buffer yet (brand new/never-edited document) is a no-op (`result: 'skipped'`), not an error - the next real edit enqueues its own job. `search_index_jobs_total{result}` (hit/miss/error/skipped... actually `success`/`skipped`/`error`) is the new metric. Retries (3 attempts, exponential backoff) are configured on the `queue.add()` call, not the processor - a thrown error inside `process()` is what lets BullMQ retry, same convention as `NotificationsProcessor`. Verified end-to-end with a real timing-sensitive e2e test: an edit is confirmed *not* searchable immediately (proving it didn't happen inline), then polled until it becomes searchable (proving the queue delivered it).

## ADR-025 — Document-tree Redis cache stores structure only, before per-user permission filtering
**Decision:** `DocumentsService.list()` caches the full (including-archived) per-workspace document set in Redis (`doc-tree:<workspaceId>`, 60s TTL as a safety net, explicit `DEL` on create/rename/move/archive/restore/publish/unpublish/restrict) and derives the `includeArchived=false` view as an in-memory filter of that one cached entry. The cache is populated/read *before* `DocumentPermissionsService.filterVisible` (ADR-022) ever runs - `DocumentsController` still calls `filterVisible` on every request, cache hit or miss.
**Reason:** The task explicitly calls out preferring to cache tree data "separately from user-specific permission filtering" - caching the *unfiltered* structure and re-applying live permission checks on every read (cache hit or not) means a stale or shared cache entry can never leak a restricted document to a user who shouldn't see it; only caching something genuinely safe to share across all callers (the raw structure) avoids having to key the cache per-user, which would both explode cache cardinality and risk staleness bugs where a permission change doesn't invalidate every affected user's entry.
**Impact:** Redis is fail-open, not fail-closed: a read or write error against Redis is caught, logged, and falls through to Postgres - `DocumentsService.list()` never surfaces a broken response because the cache was unavailable. All eight mutation methods call the same private `invalidateTree()`; a new document mutation that forgets to call it would serve a stale tree for up to the 60s TTL (not incorrect access, just stale ordering/titles) - worth a grep for `invalidateTree` when adding a ninth.

## ADR-026 — `staging` is production-like for security-sensitive checks, via one `AppConfigService.isProductionLike` getter
**Decision:** `NODE_ENV` gained a fourth valid value, `staging` (Joi schema in `env.validation.ts`). Every place that previously branched on `nodeEnv === 'production'` for a *security-relevant* behavior (refresh-cookie `Secure` flag, hiding internal error detail in `GlobalExceptionFilter`, suppressing dev-token/URL exposure in invitation responses, pino log level/transport) now branches on a new `AppConfigService.isProductionLike` getter (`nodeEnv === 'production' || nodeEnv === 'staging'`) instead.
**Reason:** Before this change, `staging` (once added as a valid value at all) would have silently inherited every "not production" convenience behavior - insecure cookies, verbose error messages, leaked invitation tokens - on what is typically a real, network-reachable deployment. Introducing the environment value without auditing every `=== 'production'` check would have been a real, shippable regression, not just an incomplete feature. One shared getter (rather than updating four call sites to a duplicated `nodeEnv === 'production' || nodeEnv === 'staging'` expression) keeps the definition of "production-like" in exactly one place.
**Impact:** `staging` and `production` are still fully independent deployments (own database/Redis/MinIO/secrets, via `.env.staging.example`, an overlay documented against the single canonical `.env.example` rather than a duplicated full copy) - `isProductionLike` only governs the small set of checks that exist purely for local-development/test convenience. Any *new* environment-gated behavior added later should be checked against this getter, not a fresh `nodeEnv === 'production'` comparison, to avoid reintroducing the same class of gap.

## ADR-027 — Drag-and-drop tree reorder via `@dnd-kit/core`, zone-based (not per-pixel) drop targets
**Decision:** Adds `@dnd-kit/core` (not `@dnd-kit/sortable` or a tree-specific package) as the only new frontend dependency for this pass. Each row is simultaneously draggable and droppable; the drop *zone* (before/inside/after) is computed from where the dragged item's center currently sits within the hovered row's rect (top/bottom quarters vs. middle half), not from a per-pixel insertion-line target.
**Reason:** ADR-012 already established the backend contract (`parentId` + optional `referenceId`/`placement`) was drag-and-drop-ready - the only real decision left was how much DnD-library machinery to take on. `@dnd-kit/core` alone (no sortable preset, no tree preset) was enough to implement draggable+droppable+collision rects directly; pulling in a heavier package for a tree-shaped list would have meant fighting its own opinions about flat-list ordering instead. The three-zone heuristic is deliberately coarser than a per-pixel insertion line - simpler to reason about, matches the "Notion-style" affordance users already expect, and needs no additional visual insertion-line component.
**Impact:** `features/documents/dragMove.ts` (`resolveDropZone`, `isSelfOrDescendant`, `computeOptimisticMove`) is pure and unit-tested, independent of dnd-kit itself - the zone math and optimistic-position math can be verified without simulating a drag gesture. The existing up/down move buttons (ADR-012) were kept, now inside each row's overflow menu, as the keyboard/no-pointer-drag path.

## ADR-028 — Server Actions pass the caller's access token through as a bound argument, not by reading the refresh cookie
**Decision:** The two new Server Actions (`inviteMemberAction`, `createWorkspaceAction` in `features/workspaces/actions.ts`) take the client's current in-memory access token as their first bound argument and forward it as a plain `Authorization: Bearer` header to `serverEnv.backendInternalUrl`. Neither reads, verifies, or rotates the `refresh_token` cookie itself.
**Reason:** This app's access tokens are deliberately in-memory-only browser state, never a cookie (Stage 2 decision, `05-frontend.md`) - a Server Action has no way to read that token except being handed it. The alternative - a Server Action independently exchanging the refresh cookie for a fresh access token - was rejected because it would race the client's own `AuthProvider` refresh-on-401 cycle over the *same* rotating refresh token; the backend's reuse-detection (rotation + revoke-all-sessions-on-reuse, `06-rules.md`) exists specifically to treat exactly that kind of double-use as a replay attack, and two independent refresh flows hitting it concurrently is a realistic way to spuriously revoke a legitimate user's session. Token passthrough keeps the Server Action to the same single authorized request the browser would have made anyway - no new trust boundary, no rotation race.
**Impact:** This is a deliberate, narrow exception to "frontend talks to the backend directly from the browser, no BFF" (`01-architecture.md`) - applied only to these two simple, non-realtime, form-shaped mutations, not a general pattern for every mutation. Yjs/document-content mutations, comments, versions, and every other authenticated call stay as client-side `apiFetch`, unchanged. A bound token can go one render-cycle stale (the Server Action re-binds on every render, not on every keystroke) - acceptable given 15-minute access token lifetimes; a stale-token failure surfaces as a normal error the user can retry, by which point `AuthProvider` has already refreshed client-side.
